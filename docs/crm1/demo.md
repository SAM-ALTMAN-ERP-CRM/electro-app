# CRM-1 Viva Demo Script

This script follows the current CRM-1 routes and seed data. It does not claim
that a missing integration succeeded. Run the application with PostgreSQL
initialized as described in [`README.md`](./README.md). For local demo mode,
`.env` should have `AUTH_REQUIRED=false`; this supplies an admin identity.

## Before the demo: check the seeded records

The requested IDs exist in CRM-1's seed data, but not all have the requested
state:

| ID | Current seeded state |
| --- | --- |
| `LEAD-0001` | Aarav Mehta, dealer source, score 70, qualified. The current score formula yields 60 for these populated fields when a lead is created or updated. |
| `OPP-0001` | Already associated to `LEAD-0001`; stage is `won`. There is no conversion endpoint. |
| `OPP-0005` | Prospect-stage opportunity; use this record for Kanban progression. |
| `QUO-0001` | Draft, 0% discount, with two items. No API updates a quote's discount. |
| `QUO-0003` | Already accepted at 10%, so it cannot demonstrate a pending approval. |
| `SO-0001` | ERP-4 seed order for `QUO-0001`; one item, total ₹42,990.00. |

To keep the specified quote ID and demonstrate the pending 10% approval, set up
`crm1_db` from the seed files, then prepare `QUO-0001` before the demo:

```sql
UPDATE quotes
SET discount_percent = 10.00,
    needs_approval = TRUE,
    approved = FALSE,
    status = 'draft',
    rejection_reason = NULL
WHERE id = 'QUO-0001';
```

This changes only the local demo database. It is necessary because the API has
no quote-edit endpoint and the seed quote is at 0%. The existing quote line
items are retained.

## Step 1 — Show a lead and its score

**Click or execute**

1. Open **Sales → Leads** (`/crm1/leads`) and locate `LEAD-0001`.
2. Verify it and the Hot threshold through the API:

```bash
curl -sS http://localhost:5101/api/leads/LEAD-0001
curl -sS http://localhost:5101/api/leads/hot
```

3. To show the live calculation rather than the seeded score, create a
   temporary lead with all scoring signals:

```bash
curl -sS -X POST http://localhost:5101/api/leads \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Viva Scoring Check",
    "source": "dealer",
    "email": "viva@example.test",
    "phone": "9000000001",
    "product_interest": "SKU-0001",
    "sales_rep_id": "EMP-0001"
  }'
```

**Expected result**

- `LEAD-0001` is returned with its seeded score `70` and appears in the Hot
  list (`score >= 60`).
- The temporary lead is created with score `60`: dealer 30 + email 10 + phone
  10 + product interest 10. Its returned ID is generated by the database.

**Verify**

- `GET /api/leads/LEAD-0001`
- `GET /api/leads/hot`
- `POST /api/leads`

**Say in the viva**

> “CRM-1 scores a lead from its source and contact/product details. Dealer
> contributes 30 points; email, phone and product interest contribute 10 each.
> A score of 60 or more is shown as Hot. The seed stores LEAD-0001 as 70,
> while the current formula recalculates those fields to 60.”

## Step 2 — Verify the lead/opportunity association

**Click or execute**

1. Open **Sales → Pipeline** (`/crm1/pipeline`) to see the opportunities.
2. Confirm the seeded association:

```bash
curl -sS http://localhost:5101/api/opportunities/OPP-0001
```

**Expected result**

The response for `OPP-0001` contains `lead_id: "LEAD-0001"`. It is already
associated in the seed. CRM-1 does not implement a separate conversion
endpoint; new links are made by setting `lead_id` on
`POST /api/opportunities` or `PUT /api/opportunities/:id`.

**Verify**

- `GET /api/opportunities/OPP-0001`
- Database row: `opportunities.id = 'OPP-0001'`,
  `opportunities.lead_id = 'LEAD-0001'`

**Say in the viva**

> “The opportunity stores a lead reference. In this build OPP-0001 is already
> linked to LEAD-0001 by seed data; there is no separate convert-lead API.”

## Step 3 — Advance an opportunity on the Kanban board

**Click or execute**

1. On **Sales → Pipeline**, locate `OPP-0005`, which is seeded in `prospect`.
2. Click **Advance Stage** once to move it to `proposal`, then again to move it
   to `negotiation`.
3. From `negotiation`, try the next advance to `won` only to demonstrate the
   quote gate. The seeded `OPP-0005` has no accepted quote, so the request
   should be rejected:

```bash
curl -i -X PATCH http://localhost:5101/api/opportunities/OPP-0005/stage \
  -H 'Content-Type: application/json' \
  -d '{"stage":"won"}'
```

**Expected result**

- The Kanban card moves `prospect -> proposal -> negotiation`.
- The request to move to `won` returns `400` with
  `Cannot close as won without an accepted quote`.
- Allowed stage moves are `prospect -> proposal`, `proposal -> negotiation`,
  and `negotiation -> won` only with an accepted quote. Active stages may move
  to `lost`; `lost` is terminal. `won` may only move to `lost`.
- `OPP-0001` is already `won`; do not use it to demonstrate forward
  progression.

**Verify**

- Kanban action: `PATCH /api/opportunities/OPP-0005/stage`
- Read state: `GET /api/opportunities/OPP-0005`

**Say in the viva**

> “The board advances one stage at a time. It does not allow skipping stages,
> and an opportunity needs an accepted quote before it can move to Won.”

The demo has now changed the in-memory/database state of `OPP-0005`. Re-run
the CRM-1 seed script before repeating this step if you need the original
prospect state.

## Step 4 — Approve and accept a 10% quote

**Prepare and click or execute**

1. Run the SQL preparation at the top of this document before starting this
   step. Refresh `/crm1/approvals` as Admin.
2. Confirm `QUO-0001` is pending, then click **Approve**.
3. Move the quote through the implemented status API:

```bash
curl -sS -X PATCH http://localhost:5101/api/quotes/QUO-0001/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"sent"}'

curl -sS -X PATCH http://localhost:5101/api/quotes/QUO-0001/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"accepted"}'
```

4. Open `/crm1/quotes` or query the quote to inspect its state and totals:

```bash
curl -sS http://localhost:5101/api/quotes/QUO-0001
```

**Expected result**

- Admin approval changes `approved` to `true`.
- A >5% draft cannot be sent before approval. The route is intended to
  transition `draft -> sent -> accepted`.
- The quote has a 10% discount. Totals are calculated from the existing quote
  items, with 18% GST on the discounted taxable value.
- **Known blocker:** verification logged a PostgreSQL error
  (`inconsistent types deduced for parameter $1`) during the quote status
  `UPDATE`. The route may return an in-memory status and attempt side effects
  while the database row remains `draft`. After each request, verify with
  `GET /api/quotes/QUO-0001`; if it still says `draft`, do not present the
  quote as persisted or the status flow as completed. This status-update bug
  needs a code fix before the full database-backed demo can pass.

**Verify**

- Pending list: `GET /api/approvals` (Admin)
- Approval: `PATCH /api/quotes/QUO-0001/approve` (Admin)
- Status: `PATCH /api/quotes/QUO-0001/status`
- Quote: `GET /api/quotes/QUO-0001`

**Say in the viva**

> “Discounts above 5% require Admin approval before the quote can be sent.
> CRM-1 calculates discount and 18% GST. The intended status sequence is
> draft-to-sent-to-accepted, but this build's database update is currently
> failing verification, so I check the returned record against the database
> before claiming it was persisted.”

## Step 5 — Check ERP-4 and CRM-3, distinguishing live data from mocks

**Click or execute**

1. After accepting the quote, inspect CRM-1 and ERP-4 logs. CRM-1 sends
   `POST /api/sales-orders` to ERP-4. Verify the existing customer order:

```bash
curl -sS 'http://localhost:5204/api/sales-orders?customer_id=CUST-0001'
```

2. Inspect the CRM-3 timeline for the customer:

```bash
curl -sS http://localhost:5103/api/customers/CUST-0001/interactions
```

**Expected result and evidence**

- The ERP-4 route is implemented. Its seed already contains `SO-0001` for
  `QUO-0001`. A new handoff using the same quote ID receives `409` because
  that quote already has an order; CRM-1 logs that it already exists. The
  seeded order is not a new order created by this demo. Its item/total also
  differs from the two-item CRM-1 quote.
- The current quote status route may still call ERP-4 after its PostgreSQL
  status update fails. Treat the ERP-4 result separately from quote
  persistence.
- If ERP-4 is unreachable and `USE_MOCKS=true`, the CRM-1 helper logs
  `[mock] used for erp4/api/sales-orders` and returns
  `services/erp4/mocks/sales-orders.json`. That is mock evidence only; it does
  not persist an order.
- CRM-1 currently calls CRM-3
  `POST /api/interactions/from-event`, but CRM-3 implements
  `POST /api/interactions` instead. A live call to the CRM-1 URL returns 404
  and CRM-1 logs `[integration-error]`; a 404 does not trigger `callService`
  mock fallback. The `timeline-event.json` file under CRM-1 is not in the
  target CRM-3 mock directory, so it is not used by this call.
- CRM-3's customer timeline may show its seeded `INT-0001` order event for
  `SO-0001` with `source_team: "ERP-4"`. That is pre-existing seed evidence,
  not a new CRM-1 event from Step 4.

**Verify**

- ERP-4: `GET /api/sales-orders?customer_id=CUST-0001`
- CRM-3: `GET /api/customers/CUST-0001/interactions`
- Logs: check for the ERP-4 duplicate message, `[mock] used ...`, or
  `[integration-error]` as applicable.

**Say in the viva**

> “CRM-1 attempts the ERP-4 handoff after acceptance. The seeded SO-0001 is
> already linked to QUO-0001, so a duplicate is expected here; if a mock is
> used, it is not a persisted order. The CRM-3 event call currently uses a
> path CRM-3 does not expose, so I cannot claim a new timeline event was
> created. That integration needs alignment before it can be demonstrated as
> a successful live handoff.”
